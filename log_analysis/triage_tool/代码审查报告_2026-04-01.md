### C-2: Session Store 并发竞态条件

**问题描述**：
`app.py` (第159行) 中的 `_store` 字典被多个线程访问，但没有任何线程同步机制。

**代码证据**：
```python
# app.py:159 - _store 定义，无锁保护
_store: dict = {}  # sid -> {'results': list, 'db_path': str, 'ts': float}

# app.py:172-173 - _set_results 写入
def _set_results(sid: str, results: list, db_path: str):
    _store[sid] = {'results': results, 'db_path': db_path, 'ts': time.time()}
    # 缺失: with _store_lock: ...

# app.py:162-169 - _get_results 读取 + 删除
def _get_results(sid: str):
    now = time.time()
    stale = [k for k, v in list(_store.items()) if now - v['ts'] > _STORE_TTL]
    for k in stale:
        del _store[k]  # 修改 _store，与其他线程并发
    entry = _store.get(sid)  # 读取 _store
    return (entry['results'], entry['db_path']) if entry else ([], DB_DEFAULT)
```

**影响**：
- 并发分析会话写入同一 session 时数据损坏
- 高并发用户负载下潜在崩溃
- 不一致的 session 状态

**竞态场景**：
```
场景1：后台线程写入时读取
T1: 后台线程开始写入 _store[sid] = {results: [...]}
T2: Flask 请求调用 _get_results(sid) 读取
T3: 读取器看到部分写入的数据（results 不完整）
T4: 用户点击进入 /errors，读取到损坏的数据

场景2：TTL 清理与并发访问冲突
- 如果另一线程正在访问被删除的 sid，可能导致 KeyError 或读到空数据
```

**备注**：已存在独立的 Bug 文档 (`BUG-XXX_store并发访问竞态条件.md`) 但修复未实施。

**建议**：为所有 `_store` 读/写操作添加 `threading.Lock()`。

### C-3: 知识库写入操作缺乏原子性保证

**问题描述**：
`_FileLock` 实现存在关键缺陷 - 锁文件创建使用 `O_EXCL` 但未对实际的 Excel 写入操作提供原子性保证。

**代码证据** (`core/db_manager.py` 第32-58行)：
```python
def __enter__(self):
    # ... 锁文件获取 ...
    self._fd = os.open(self.lock_path, os.O_CREAT | os.O_EXCL | ...)
    return self  # 锁已获取，但 Excel 尚未写入

def __exit__(self, exc_type, exc_val, exc_tb):
    # 锁在 Excel 保存后释放
    # 如果进程在锁获取和保存之间崩溃：
    # 1. 锁文件残留（stale）
    # 2. Excel 文件可能损坏
    # 3. 下一个进程等待 60s 后清除 stale 锁
```

**影响**：
- 崩溃期间数据损坏风险
- 60秒 stale 锁超时导致长时间不可用
- 网络共享场景更脆弱

**建议**：实现预写日志或事务文件模式（写入 `.tmp`，然后原子重命名）。

## 二、高危问题 (Severity: High)

### H-1: Session Store 清理内存泄漏

**问题描述**：
`_get_results()` 仅在访问时清理过期条目（app.py 第164-167行）。不频繁访问的会话无限期累积，直到重启。

**代码证据**：
```python
def _get_results(sid: str):
    now = time.time()
    stale = [k for k, v in list(_store.items()) if now - v['ts'] > _STORE_TTL]
    for k in stale:
        del _store[k]
    # 问题：只有调用 _get_results 时才清理
```

**影响**：
- 随时间推移内存无界增长
- 创建许多会话但不访问时 DoS 可能性
- 最终导致服务器崩溃

**建议**：实现定期后台清理线程或使用 `weakref.WeakValueDictionary`。

---

### H-2: 全局配置变更无线程安全

**问题描述**：
运行时修改全局列表 `EXTRA_PATTERNS` 和 `PASS_PATTERNS` 时缺乏适当的同步。

**代码证据** (`app.py` 第738-795行)：
```python
EXTRA_PATTERNS: list = _load_extra_patterns()  # 全局

@app.route('/extra_patterns/add', methods=['POST'])
def extra_patterns_add():
    with _extra_patterns_lock:
        EXTRA_PATTERNS.append(kw)  # 线程安全
        _save_extra_patterns(EXTRA_PATTERNS)  # 但是...
        # 磁盘写入期间持有锁
        # 并发读取操作（如分析期间）可能读取不一致状态
```

**影响**：
- 分析可能使用过时或不一致的配置列表
- 配置更改与活动分析之间的竞态条件

**建议**：使用读时复制模式或不可变配置快照。

### H-3: 错误处理不一致

**问题描述**：

**影响**：
- 不一致的用户体验
- 某些错误导致 HTTP 500 而无有用消息
- 调试困难

### H-6: 并行解析中错误恢复不足

**问题描述**：
`parse_logs()` (`log_parser.py` 第183-213行) 使用 `ThreadPoolExecutor`，但单个文件解析失败不会正确传播。

**代码证据**：
```python
for future in as_completed(future_to):
    i, fp = future_to[future]
    r = future.result()  # 这会引发异常，但 try/except 在哪里？
    results[i] = r
```

如果一个文件失败（损坏、权限），整个批次可能失败或产生不完整结果。

**影响**：
- 单个坏文件阻塞整个分析
- 用户体验差
- 难以识别导致失败的文件

**建议**：用 try/except 包裹 `future.result()`，记录错误，继续处理剩余文件。

    r'(UVM_(?:ERROR|WARNING|FATAL))\s+(\S+)\((\d+)\)\s+@\s+([\d.]+\s*\w+):\s+(\S+)\s+\[(\w+)\]\s*(.*)',

- 大日志文件上性能次优
- 解析期间较高的 CPU 使用率

## 七、性能分析

### 识别的瓶颈：

| 瓶颈 | 位置 | 影响 |
|---|---|---|
| 知识库加载 | `db_manager.py` | 每次写入操作加载完整 Excel |
| 正则匹配 | `log_parser.py` | 大文件的每一行使用复杂正则 |
| 线程池并发 | `log_parser.py` | 未针对不同硬件调优 |
| SSE 轮询 | `app.py:404` | 0.3s 间隔可能效率低 |

### 可扩展性关注点：

1. **内存 Session Store**：不适合分布式部署
2. **单进程 Flask**：无 Gunicorn/uWSGI 多 Worker 配置
3. **无缓存**：重复分析重新解析相同文件
4. **无队列系统**：后台任务由简单线程管理

## 十一、结论

triage_tool 应用具有**扎实的基础**，结构清晰的核心模块（log_parser、matcher、db_manager）和对需求的全面理解（PRD）。然而，**文档计划与实际实现之间存在显著差距**，特别是 LLM 集成完全缺失。

**关键架构问题**（线程安全、原子写入、输入验证）应在生产部署前解决。应用将受益于**现代化**，如错误处理、日志记录、测试和安全加固等领域。

LLM_INTEGRATION_PLAN 代表深思熟虑的扩展策略，将显著增强用户价值。实施是可行的，但需要对并发性、成本管理和错误处理进行仔细关注。

**总体评估**：应用对于**基本用例在功能上是完整的**，但对于**生产级部署和完全 PRD 合规**需要加固和功能完成。

### C-1：P6 review job 运行中切换 profile / 保存 config 互锁完全失效

**位置**：[blueprints/llm_bp.py:554-571](blueprints/llm_bp.py#L554-L571) vs [1320-1419](blueprints/llm_bp.py#L1320-L1419)

**问题**：`_running_jobs_summary()` 检查的是 P6 任务的 `phase` 字段：

```python
# llm_bp.py:561-570
with _review_lock:
    for jid, job in _review_jobs.items():
        phase = job.get('phase', '')                    # ← 读 phase
        if phase and phase not in ('done', 'error', 'stopped'):
            summary.append({...})
```

而 `_run_review_job` 实际上从未写过 `phase` 字段，全程用 `status`：

```python
# llm_bp.py:1336, 1355, 1418-1419
_upd({'status': 'error', 'reason': str(e)})
_upd({'status': 'running', 'total': total_groups, ...})
_upd({'status': 'done', 'done': total_groups, ...})
```

前端 [index.html:1629](templates/index.html#L1629) 也用 `d.status === 'done'`。所以 `_running_jobs_summary` 对 P6 review 任务**永远返回空列表**（`if phase and ...` 因 `phase = ''` 短路为 False）。

**影响**：

- `/llm/save_config`、`/llm/profile/update`、`/llm/profile/delete`、`/llm/profile/activate` 的"运行任务保护"分支完全不会触发
- 用户在 P6 跑了几分钟时切换到另一个 profile：已 in-flight 的线程仍用启动时快照的 `cfg`（[llm_bp.py:1482](blueprints/llm_bp.py#L1482) thread args 传 cfg），但 `llm_client._config` 已被改成新 profile 的字段
- `_run_review_job` 内调 `llm_client.call_llm_with_cache(...)`（[1393](blueprints/llm_bp.py#L1393) 行），这里读的是 `llm_client._config`（不是传入的 cfg）—— 所以 P6 实际上**一半 batch 用旧 endpoint、一半用新 endpoint**，结果错乱且无错误提示
- PRD v2.3 / LLM_INTEGRATION_PLAN v4.7 / LLM_USAGE_GUIDE 三份文档都明确说"P6 跑时禁止切 profile" — **契约破裂**

**建议**：统一字段命名为 `status`：

```python

status = job.get('status', '')
if status and status not in ('done', 'error', 'stopped'):
    summary.append({
        'kind':     'P6_kb_review',
        'job_id':   jid,
        'phase':    status,          # 前端兼容字段名保留 phase
        'progress': job.get('done', 0),
    })
```

并补单测：调 `/llm/kb_review` 后立即调 `/llm/profile/activate`，断言返回 `need_force=True`。

## High

### H-1：`_parse_json_safe` 贪婪正则在「解释 + JSON」混合输出下退化为 None

**位置**：[blueprints/llm_bp.py:533-542](blueprints/llm_bp.py#L533-L542)

```python
def _parse_json_safe(text: str, array: bool = False):
    pattern = r'\[.*\]' if array else r'\{.*\}'
    m = re.search(pattern, text, re.DOTALL)
    if not m:
        return None
    try:
        return json.loads(m.group())
    except Exception:
        return None
```

`\{.*\}` 加 `re.DOTALL` 是**贪婪**匹配——抓从第一个 `{` 到**最后一个** `}` 的最大区间。实战场景：

- LLM 返回 `好的，我的判断：{"ranked": [0,1]}\n\n这里解释一下：当 {a} 不等于 {b} ...`
- 匹配区间：`{"ranked": [0,1]}\n\n这里解释一下：当 {a} 不等于 {b}`（含 `}{` 混杂）
- `json.loads` 失败 → 返回 None
- 路由静默降级到默认值（P1 退到 `list(range(N))`、P5 退到空列表、P6 退到无 pairs）

**影响**：

- 影响所有 6 条调用方：`/llm/rank_entries`（[871](blueprints/llm_bp.py#L871)）、`/llm/custom_extract`（[1068](blueprints/llm_bp.py#L1068)）、`/llm/similar_errors`（[1186](blueprints/llm_bp.py#L1186)）、`/llm/batch_patterns`（[1259](blueprints/llm_bp.py#L1259)）、`/llm/semantic_query`（[1307](blueprints/llm_bp.py#L1307)）、`/llm/kb_review` worker（[1398](blueprints/llm_bp.py#L1398)）、`/llm/merge_suggest`（[1452](blueprints/llm_bp.py#L1452)）
- 现象：用户偶尔感觉 "AI 没说话"，但 LLM 实际返回了正确 JSON，只是被解析逻辑丢弃
- 缺乏错误日志——降级路径是 `parsed = _parse_json_safe(raw) or {}`，无可观测性

**建议**：

```python
def _parse_json_safe(text: str, array: bool = False):
    if not text:
        return None
    # 先剥 markdown 代码块（LLM 常用 ```json ... ``` 包裹）
    fence = re.search(r'```(?:json)?\s*\n?(.*?)```', text, re.DOTALL)
    if fence:
        text = fence.group(1)
    open_ch, close_ch = ('[', ']') if array else ('{', '}')
    # 配对计数找首个完整 top-level 对象/数组
    start = text.find(open_ch)
    if start < 0:
        return None
    depth, in_str, esc = 0, False, False
    for i in range(start, len(text)):
        c = text[i]
        if esc:
            esc = False; continue
        if c == '\\' and in_str:
            esc = True; continue
        if c == '"':
            in_str = not in_str; continue
        if in_str:
            continue
        if c == open_ch: depth += 1
        elif c == close_ch:
            depth -= 1
            if depth == 0:
                try:
                    return json.loads(text[start:i+1])
                except Exception:
                    return None
    return None
```

### H-2：`update_profile` / `save_config` / `add_profile` 写文件与 reload 之间存在多线程 race

**位置**：[core/llm_client.py:247-248](core/llm_client.py#L247-L248)（save_config）、[270-271](core/llm_client.py#L270-L271)（add_profile）、[300-301](core/llm_client.py#L300-L301)（update_profile）

```python
_write_file({'active_profile': active, 'profiles': profiles})  # 写磁盘 — 无锁
reload_config()                                                # 内部加 _lock
```

`_write_file` 不在 `_lock` 内（参考 [_write_file](core/llm_client.py#L125-L132)）。两个线程并发改 profile 时：

1. Thread A: `_write_file(A_state)`
2. Thread B: `_write_file(B_state)` — 磁盘最终是 B
3. Thread A: `reload_config()` — 读到 B 的磁盘内容、写入 `_config`
4. Thread B: `reload_config()` — 又读一遍、写入 `_config`

结果：磁盘内容 = B，但 _config 可能反映 A 的中间状态（取决于调度）。更糟：如果 thread A 是 add，thread B 是 delete，A 的新 profile 可能被 B 的磁盘内容直接吃掉。

**影响**：实际触发概率低（用户不会并发改 config），但若被脚本批量调用 `/llm/profile/*` 端点则可见。返回 `{ok: true}` 但磁盘状态不可预测。

**建议**：把整段 read→mutate→write→reload 都包进一个**模块级 mutation_lock**（与 `_lock` 区分，避免阻塞读路径）：

```python
_mutation_lock = threading.Lock()  # 仅保护配置写路径

def update_profile(name, fields):
    with _mutation_lock:
        raw = _load_file()
        profiles, active = _migrate_or_validate(raw)
        # ... 现有变更逻辑
        _write_file({'active_profile': active, 'profiles': profiles})
        reload_config()
```

### H-3：损坏 `llm_config.json` 静默覆盖，旧配置丢失

**位置**：[core/llm_client.py:113-122](core/llm_client.py#L113-L122)

```python
def _load_file() -> dict:
    if _base_dir is None:
        return {}
    p = _base_dir / 'llm_config.json'
    if not p.exists():
        return {}
    try:
        return json.loads(p.read_text(encoding='utf-8'))
    except Exception:
        return {}
```

JSON 解析失败 → 静默返回 `{}` → `_migrate_or_validate({}) = ([], '')`。

**触发链**：

1. 用户手工编辑 `llm_config.json` 时多打一个逗号 / 漏一个引号
2. 重启或点 "重载配置" → `_load_file` 返回 `{}` → UI 显示"未配置"
3. 用户以为"那就重新输入吧"，在 UI 填入新 profile 点保存
4. `save_config` → `_load_file` 又返回 `{}` → `profiles = []` → 把用户填的新 profile 写盘
5. **原文件内容（含 API key 等敏感数据）被静默覆盖**，且没有 .bak 之类的回滚路径（`llm_config.json` 不像 `error_db.xlsx` 有滚动备份）

**影响**：

- 重要：API key 丢失后用户得重新申请
- 重要：多 profile 配置全部丢失（用户可能有 5 个不同 endpoint 的 profile，因一个 typo 全没）

**建议**：

1. 解析失败时把损坏文件 rename 到 `llm_config.json.broken.{timestamp}` 备份后再继续
2. UI 顶部加一条警告条："上次启动时检测到 llm_config.json 解析失败，备份至 llm_config.json.broken.20260511..."

```python
def _load_file() -> dict:
    if _base_dir is None:
        return {}
    p = _base_dir / 'llm_config.json'
    if not p.exists():
        return {}
    try:
        return json.loads(p.read_text(encoding='utf-8'))
    except Exception as e:
        try:
            broken = p.with_suffix(f'.json.broken.{int(time.time())}')
            p.rename(broken)
            global _last_load_error
            _last_load_error = f'JSON 解析失败，原文件已备份到 {broken.name}: {e}'
        except OSError:
            pass
        return {}
```

并暴露 `_last_load_error` 给 `/llm/get_config` 响应。

### M-4：P2 prescan 内存随匹配行数线性增长，违反 PRD"恒定内存"承诺

**位置**：[blueprints/llm_bp.py:215-250, 387-418](blueprints/llm_bp.py#L215-L250)

`_p3_prescan` / `_p3_prescan_blocks` 都把每个命中行的权重塞进 `weights` / `kw_weights` dict，行号是 key。10 GB 日志每隔几行命中关键词时，dict 可达 GB 级。

**对比**：PRD §2.2 / log_parser.py 明确声明"streaming line-by-line, constant memory"。P2 prescan **不满足此承诺**。

**影响**：

- 实测可触发：用户对 5 GB 大日志查询常见词（"error" / "fail"），prescan 阶段进程内存膨胀
- 错误模式：内存超限被 OOM killer 干掉 → 进程消失，前端轮询超时

**建议**：

只保留**滑窗内**的权重（窗口大小 = max_lines）。需要重构 `_p3_prescan` 为两阶段：

1. 一次流式扫描，仅记录"top-K 候选锚点"（堆维护）
2. 第二次扫描仅在候选行附近聚合权重

或：每读 N 行清理一次"距当前行 >2 × max_lines"的旧锚点（远超窗口范围的不可能进入最终结果）。

### M-6：`update_profile` rename 后激活指针更新逻辑可疑

**位置**：[core/llm_client.py:290-298](core/llm_client.py#L290-L298)

### M-7：`matcher.score_query` 活跃度融合在 `relevance=0` 时已正确剔除，但活跃度信号在排序中可能压倒强相关条目

**位置**：[core/matcher.py:104-133](core/matcher.py#L104-L133)

```python
final = relevance * (1.0 + 0.5 * boost)
```

边缘场景：

- 条目 A：relevance=2，boost=0     → final=2
- 条目 B：relevance=1，boost=1.0   → final=1.5

✅ 强相关仍优先。

但若：

- 条目 A：relevance=2，boost=0     → final=2
- 条目 B：relevance=2，boost=1.0   → final=3

✅ 同相关度时活跃优先。这是设计意图。

**潜在问题**：boost = `min(hit_7d / 5, 1.0)`（kb_stats.py:212）。5 次 7 日内命中即封顶。对一个老 KB（数千条），可能很多条目 boost 都顶到 1，导致"7d 命中过 5 次的所有条目"区分不开。

**建议**：boost 改为对数缩放或更高阈值，例如 `min(math.log1p(hit_7d) / math.log1p(50), 1.0)` 让活跃度有更宽的层次。或在 PRD v2.4 写明本期 v1 设计就是粗粒度，待 v2 细化。

长期运行进程下，每出现一个新的 `db_path`，缓存条目永久驻留。多用户共享时不致命，但建议 cap 到 32 条（LRU）。

### L-3：散布的 `print()` 缺统一日志框架（沿袭自 2026-04-02 M-3）

待统一改 `logging` + 文件 handler + rotation。本轮无新增 print 但旧问题未解决。

### L-4：`_get_file_paths` docstring 描述与实际行为不符

**位置**：[state.py:215-219](state.py#L215-L219)

```python
def _get_file_paths(sid: str) -> list:
    """返回当前会话的文件路径列表（路径模式有值，上传模式为空）。"""
```

c552c5f 之后上传模式也填充 file_paths。建议把 docstring 改为："两种模式均填充；上传模式存 UPLOAD_DIR 下的路径，路径模式存用户提供的实际路径"。

### L-5：`_validate_db_path` 标榜"防穿越"实则只校验后缀和绝对路径

**位置**：[state.py:175-188](state.py#L175-L188)

`/etc/secrets.xlsx`、`\\\\..\\..\\` 在 UNC 下都能通过。用户提供了路径，工具按命运执行——这是设计，但 doc 字面"防止路径穿越攻击"误导。建议 doc 改为："限制后缀和绝对路径；不限制目录，由 OS 权限决定可达性"。

### L-6：`kb_review_export` 在 job 仍 running 时也可下载（仅部分结果）

**位置**：[blueprints/llm_bp.py:1528](blueprints/llm_bp.py#L1528) 

```python
if not job or job.get('status') not in ('done', 'running'):
```

允许 running 状态导出。功能上用于"边跑边看"，但若用户预期"导出 == 完成"会困惑。建议响应里携带 `partial: true` 标志。

### L-7：`record_event` 异常吞噬过宽，丢失运维信息

**位置**：[core/kb_stats.py:80-82](core/kb_stats.py#L80-L82)

权限错误、磁盘满、网络分享掉线 — 全静默。建议至少 print 一次（带 throttle）便于运维定位。
